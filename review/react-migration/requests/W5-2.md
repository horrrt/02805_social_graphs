## 4. NetworkView: a failed d3 stays failed

**Status:** open. W5-2 works around it in the same shim (`src/features/week05/map/NetworkView.tsx`), with
`d3Store` in `src/features/week05/map/store.js`.

**File:** `src/kit/NetworkView.tsx` (K2), with a module store beside it (`src/kit/network/state.ts` or a new
`src/kit/network/d3.js`).

**Why.** G5 `faults.mjs --data --files '*d3-7.9.0.min.js'` on Week 5 failed with kit NetworkView:
`w5-base/24` and `w5-base/26` (the relations map's kind switch) show `requests:…/d3-7.9.0.min.js: 0 -> 1`.
graph.js `loadD3()` keeps its promise in `d3Loading`, a rejected one too, so main asks for d3 once per page
and never again after it fails. NetworkView loads d3 through `useVendor`, and `loadVendor` evicts a failed
file, so every NetworkView mounted after the failure requests it again. Week 5's relations map mounts a new
view on each switch, as `marvelMap()` drew a new one on main, so head makes more requests than base. On the
happy path nothing changes. With the patch the fault run is `ok`.

**Patch.**

```diff
--- a/src/kit/NetworkView.tsx
+++ b/src/kit/NetworkView.tsx
@@
+import { createStore } from "@/scripts/runtime/store.js";
+import { useStore } from "@/lib/useStore";
@@
 type D3 = any;
+
+// d3 failing to load, kept for the page as graph.js loadD3() kept its rejected
+// promise, so no view drawn later asks for it again.
+const d3Store = createStore({ failed: false });
+const d3FailedOf = (s: { failed: boolean }) => s.failed;
@@
-  const d3 = useVendor<D3>("d3-7.9.0.min.js", "d3", { enabled: explore });
+  const d3Failed = useStore(d3Store, d3FailedOf);
+  const d3 = useVendor<D3>("d3-7.9.0.min.js", "d3", { enabled: explore && !d3Failed });
+  useEffect(() => {
+    if (d3.status === "error") d3Store.setState({ failed: true });
+  }, [d3.status]);
```
